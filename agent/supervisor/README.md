# supervisor

Stream-json wrapper for the Edva ops-agent. Spawns `claude -p` with structured I/O, parses events, dispatches messages via HTTP.

## Why this exists

Before: ops-agent ran in a tmux pane. Gmail pushes arrived via `gmail-channel` MCP server which emitted `notifications/claude/channel` to nudge the agent. Watchdog detected stuck states by regex-scraping pane content. Permission prompts were auto-accepted via tmux keystrokes.

After: supervisor owns the child `claude` process via stream-json. Gmail pushes and webhooks are serialized onto the agent's stdin as user messages. Watchdog just `curl`s `/health`. No TTY prompts, no pane-scraping, no race conditions.

## Layout

```
index.mjs          — glue: parse args, spawn child, wire HTTP, handle signals
claude-session.mjs — spawn claude, parse stream-json stdout, emit events
dispatcher.mjs     — serialize turns: queue until previous result event arrives;
                     optional preamble(item) hook prepends a live-state block at send time
dispatch-preamble.mjs — buildPreamble()/shouldPreamble(): tiny <live-state> block (home-tz now)
                     prepended per non-control turn; kill via OPS_DISPATCH_PREAMBLE_DISABLED=1
http-server.mjs    — HTTP endpoints (9090 gmail, 9092 webhook, 9093 control)
gmail-source.mjs   — dedup historyIds, save last-history, honor pause flag
_ext/              — the instance's own hooks (optional; contract in _ext/.gitkeep):
                     gmail-intake.mjs (an intake step ahead of the P1 stampers),
                     routes.mjs (extra :9090 POST routes + an email-inbound pre-route)
event-log.mjs      — append events.ndjson + cost.ndjson (fire-and-forget); also tees
                     every event into the events_fts recall index (../../lib/event-fts.mjs)
handoff-digest.mjs — session-handoff digest, built in code from the outgoing
                     session's activity and prepended to the fresh one's first dispatch
state.mjs          — session_id + cumulative cost + dispatch count (rotation) + tool-turn count (telemetry)
mcp-config.json    — MCP servers loaded for the child (currently empty; regular MCP connectors are loaded from user config)
```

## HTTP API (port 9093)

- `GET  /health`   → `{sessionId, model, uptimeMs, lastEventAgeMs, totalCostUsd, totalTurns, totalDispatches, maxSessionTurns, contextTokens, queueDepth, inFlight, childAlive, ...}`
- `GET  /cost`     → `{todayUsd, weekUsd, totalUsd, perModel}`
- `POST /restart`  → graceful restart (watchdog uses this on stale-event detection)
- `POST /dispatch` → `{content, source}` manual dispatch

Ports 9090 (gmail) and 9092 (webhook) accept POSTs identical to the old channel servers. The Gmail-push ingress arrives via a Cloudflare Tunnel (the push hostname → `:9090`, OIDC-verified); cron scripts and the CF Email Worker don't need to change.

**Instance hooks.** Behaviour that belongs to one installation (a sender whose mail is filed in code, an extra webhook on the tunnel) lives in `_ext/`, not in the kernel files. `gmail-source.mjs` runs `_ext/gmail-intake.mjs` `intake()` after the spam check on both intake paths and skips the dispatch when it returns `{handled: true}` (fail-open). `http-server.mjs` loads `_ext/routes.mjs` `register(api)` at import: `api.post(path, handler)` claims a POST path on `:9090` ahead of the email-inbound and Gmail-push branches (the handler authenticates its own caller), and `api.emailInbound(fn)` may claim an authenticated inbound email before the alignment gate. Identity (the agent's address, the owner's name and address, the home timezone, the Supabase project) comes from `lib/instance.cjs`.

## State files

- `state/ops/session.json` — session_id + cumulative cost (persistent across restarts)
- `state/ops/handoff-digest.json` — last session-handoff digest (for observability / re-read)
- `../logs/supervisor-ops/events.ndjson` — full event firehose (durable source of truth for the `events_fts` recall index)
- `../logs/supervisor-ops/cost.ndjson` — one line per turn completion

## Run

```bash
node index.mjs --agent ops                # production
node index.mjs --agent ops --model sonnet # dev
node index.mjs --agent ops --no-resume    # start fresh session
```

## Context management (bounding per-turn cost + preserving continuity)

The supervisor `--resume`s one Claude session across dispatches, so its context — and therefore the cost of every turn — grows with the number of turns. Ops dispatches are usually spaced further apart than the 5-min prompt-cache TTL, so each turn cold-re-bills the whole accumulated prefix at full input price. Left unbounded this produces a cost runaway ($6–25/turn on a session of a few hundred turns).

The **primary** bound is now the context guard, which shrinks context *without* losing continuity; the rotation mechanisms below are the coarse backstop.

- **Context guard (primary, ported from chat).** `startContextGuard()` tracks `contextTokens` off per-assistant-call usage (input + cache-read + cache-create = the live prompt). When the dispatcher is idle and context crosses the compact threshold (170k) with enough conversation above the measured floor, **ops** injects `/compact` — the model summarizes in place, the `sessionId` survives, and the re-billed prefix drops. **ops-light and ops-haiku rotate instead** (`compactOnContext: false` in `agents.json`): their cron jobs keep state in playbooks and files, so a compact summary is never read back and only adds ~9.5k output tokens before the next dispatch's cold write anyway. Above 185k every tier hard-rotates. Rule + rationale: `context-guard.mjs`. Thresholds/timing are env-overridable: `OPS_CONTEXT_COMPACT_TOKENS`, `OPS_CONTEXT_ROTATE_TOKENS`, `OPS_MIN_COMPACTABLE_TOKENS`, `OPS_CONTEXT_GUARD_INTERVAL_MS`, `OPS_COMPACT_COOLDOWN_MS`. `contextTokens` shows in `/health`.

Rotation to a fresh session (fresh `sessionId` ⇒ empty context) remains as a backstop:

- **Dispatch-count rotation.** `maxSessionTurns` in `agents.json` (the key kept its old name) counts **dispatches**: ops/ops-light `40`, ops-haiku `30`; `0` disables. Once `totalDispatches ≥ cap`, `_maybeRotateForTurnCount()` rotates in the `turn_complete` handler — **at a turn boundary, even when the queue is non-empty.** Queued items transfer to the fresh session via the normal restart-recovery path; nothing is lost or double-run. Uses `restart({skipBackoff:true})`. It deliberately does not compare `totalTurns` (`num_turns` summed, i.e. tool steps): one 20-step job would use up ops-haiku's whole cap and the tiers would rotate every few dispatches. `totalTurns` is still recorded, for telemetry only.
- **Age-based rotation.** `startRotationTimer` — soft at 20h (defers while busy), hard at 30h (rotates regardless).
- **Cold-start guard.** `main()` refuses to `--resume` a persisted session already past the dispatch cap.

**Session-handoff digest (model-free).** A blunt rotation is amnesia — the fresh session boots knowing nothing of what the old one was doing. Before a *healthy* rotation (dispatch cap / age / manual / context — **not** crash-loop or auth outage, which are degraded states), `_prepareHandoff()` builds a digest in code (`handoff-digest.mjs`: the distinct recent job sources plus the last dozen lifecycle lines, from the `events_fts` recall index with an `events.ndjson` tail fallback) and stages it; the dispatcher preamble then prepends it **once**, as a `<session-handoff>` block, to the fresh session's first real dispatch. It is persisted to `state/<agent>/handoff-digest.json` and logged as `session_handoff.injected`. Kill-switch: `OPS_HANDOFF_DISABLED=1`.

It is not a forked Haiku `claude -p` rewriting the activity as prose plus a whole turn whose only job is "acknowledge in one line": that costs a cold cache-write of the fresh floor per rotation, cannot add information (rotation only fires when idle, so the input is completed dispatches), never reaches `job-costs.ndjson`, and such a turn tends to act on the digest (re-investigating completed work). The block is framed as background only, with nothing to act on — the System Channel rule in `agent/CLAUDE.md` gives recurring problems to `system-issue-review` and outages to `watchdog.sh`.

**Background-wake attribution.** A `run_in_background` task or async subagent that finishes after its dispatch ended wakes the model with a `<task-notification>`, and that turn completes with no in-flight item. The supervisor maps each task id to the dispatch source that launched it and charges the wake turn to that source in `job-costs.ndjson` (`bg_wake: true`), instead of the unattributed `-` row it used to be.

**Stable prompt prefix.** The child is spawned with `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1`, which turns off claude's session-start `git status` / recent-commits snapshot (and its generic git instructions). The repo always has churning untracked `data` files and new commits, so that snapshot made every fresh session's prefix differ and the CLAUDE.md chain behind it was re-written to cache instead of read. The child also gets `--exclude-dynamic-system-prompt-sections` (agents.json `excludeDynamicPromptSections`, default on), which moves today's date, cwd and env info out of the system prompt into the first user message — otherwise the first session of every day re-wrote the floor. It is only passed when `claude --help` lists the flag (`supportsCliFlag` in `claude-session.mjs`), so a stale CLI degrades to "not passed" rather than a crash loop. Self-authored `ext/` tools are served by `tools-mcp` in name order so the tool block is byte-stable too. Out of our hands: the order in which the CLI merges tools across MCP servers.

**Gmail triage runs on ops-light.** gmail-source lives in the ops supervisor (it owns the Pub/Sub port), but each per-message triage dispatch (`gmail:<messageId>`) is POSTed to the ops-light webhook by `triage-route.mjs` — same model and CLAUDE.md, `--effort medium`, no Chrome. Mail addressed to Edva (command channel) and batch/catch-up/storm dispatches stay on ops; an unhealthy ops-light or a failed POST falls back to the ops dispatcher. The dispatch-attempt counter is recorded before routing and the RECLASSIFY counter is a shared file, so loop-breakers work across tiers. Config: agents.json `ops.gmailTriageTarget` (`"ops"` = rollback, restart ops).

**Mail to Edva's own address runs outside the session.** `/email-inbound` spawns `bin/email-inbound-run` (stateless one-shot, explicit read-only MCP grant) and only escalates action requests into the ops session. Config: agents.json `ops.emailInboundMode` (`"session"` = rollback). See `ops-agent/jobs/email-inbound.md`.

**A refused quota holds the queue.** When the Max allowance is used up, `claude -p` answers a turn in well under a second with a `rate_limit_event` of `status: "rejected"` and an ordinary-looking result. Without a hold the dispatcher would record that as finished work (dozens of dispatches, Gmail triages included, lost in one outage). Now `dispatcher.mjs` puts the refused item back at the head of the queue and **holds** dispatch until the window's `resetsAt` + 1 min (15 min when the event gives no reset time; capped at 8 days). The hold is separate from the auth `paused` flag, so neither clears the other. A rejection while overage is in use is not a refusal. A turn that hit the limit after it had already run tool calls (`num_turns` > 1) is **not** re-run, because repeating it could repeat its side effects; it completes as before and only the hold applies. The CLI announces a refusal only once per process (one event, then silent refusals), so the first turn after a hold is a **probe**: if it never got past its first call and either ended `terminal_reason` `"api_error"`/`"blocking_limit"` or billed nothing (the process's cumulative `total_cost_usd` did not move, or is 0 on a fresh process; the reason string has differed across CLI versions, the cost has not), it is treated as still refused and re-held, and no ✅ is sent. The cost test needs exactly one turn, because a no-op `/compact` reports zero turns with a flat total. The context guard queues nothing while held, and a context-guard turn neither settles the probe nor counts as recovery. Outside that probe nothing second-guesses a result. Known limit: if auth breaks during a probe, the probe reads it as quota and re-holds, so the 3-strike auth-outage alert arrives about 45 minutes later than it otherwise would. While held, a dispatch identical to one already waiting (same source, same text) joins it rather than stacking, so a 15-minute cron cannot pile up ~150 copies over a weekly reset. The supervisor re-applies the hold to the replacement dispatcher after any restart, so a watchdog restart during the outage does not send another turn, and a refused turn never counts toward `consecutiveNoOpTurns`. One `⚠️` system row with a push per outage (no tier name in the text, so ops, ops-light and ops-haiku dedup to a single page); a silent `✅` when the first real turn completes afterwards. `/health` shows `rateLimitHoldUntil`, and `dispatcherPaused` is true during a hold, which already stops hum from queueing moments and makes the watchdog's backlog alert name a paused dispatcher. Test: `agent/test/supervisor-quota-hold.test.mjs`.

**Chat holds too, and never relays the CLI's limit message.** Otherwise chat's safety net posts the CLI's "You've hit your weekly limit · resets …" text to the user as the answer to their message, which is then never answered. `chat-supervisor.mjs` now reads a refusal from structure only, reusing ops' `isQuotaRefusal` / `rateLimitHoldUntil`: a rejected `rate_limit_event` during the turn, or the CLI's synthetic assistant message carrying `error: "rate_limit"` (most refused chat turns carry the message, some with no event; a `/compact` can carry only the event). That message's text is never collected for the safety net. A refused turn that did no work goes back to the front of its priority band **once**, with a `[supervisor]` header saying it is being answered late; refused again on that retry it is dropped and the user is told to resend, so nothing loops. A turn that already ran tool calls is not re-run. `PriorityDispatcher` gained `hold()` / `releaseHold()` / `isHeld()` and `requeueInFlight({ front })`; the deadline and its timer live on the supervisor, which re-applies them to the replacement dispatcher after a restart. While held, the context guard does nothing and a restart queues at most one init. The user gets **one plain line per outage** in their current time zone (`user-timezone.json` via `hum-events.mjs` `userTz()`), posted like the auth notice, when their message is refused, when a background turn is refused while their message waits behind it, or when they write during a hold: "I've hit this week's Claude limit, so I can't answer right now. It resets at 11pm your time, and I'll pick your message up then." A message set aside after its one retry gets a "set aside" line, **at most one per outage**: a later message set aside in the same outage is dropped the same way and logged (`set-aside notice already sent this outage`, event `quota_notice_suppressed`), not announced. The outage (hold deadline, limit info, which of the two lines went out) is saved in `session.json` under `quotaOutage` on every change and removed when the limit clears, so a new supervisor process started mid-outage re-arms the hold and sends neither line again (`quota outage restored from session.json`, event `quota_restored`); one whose hold ended more than 6 hours earlier is dropped as stale, and a restored hold is capped at 8 days like any other. A restart therefore no longer clears a wrong hold; removing `quotaOutage` from `agent/supervisor/state/chat/session.json` and restarting does. Log lines: `RATE LIMIT: {...}` (same as index.mjs), `QUOTA REFUSED: ...`, `quota notice to <user>: ...`, `quota hold released`, `quota cleared`; `/health` shows `rateLimitHoldUntil`. No fallback model, ever. watchdog.sh leaves a holding chat alone: its stale check (queue waiting 10 minutes with no child events), which has no cooldown on chat and would otherwise restart it every 2-minute tick until the reset, skips the restart while `/health` shows `rateLimitHoldUntil` and logs that it did. Any other restart keeps the hold, sends no turn and posts no second line. A restart now drains the handed-over queue only after its listeners are attached; before, the first handed-over item (for instance a message whose hold ran out mid-restart) ran with no tracked turn, so no safety net and no hang timer. Chat's result listener also skips a zero-work result while a turn is in flight (a `--resume` handshake after a turn-watchdog kill, or a no-op `/compact` on a fresh session), as the dispatcher does (`lib/phantom-result.mjs`), unless it is an auth failure; otherwise it would clear the tracked turn, leaving that turn with no safety net and no hang recovery (a guard against a rare gap). The CLI also uses the `rate_limit` error class for "Usage credits required for 1M context" (which would otherwise be relayed raw); that reads as a refusal too: a 15-minute hold, one retry, then set aside with a note that names the usage limit, and the context guard, whose compaction is the real remedy there, idles during the hold. Known limits: the queue lives in memory, so a reboot or crash mid-hold loses a waiting message (a code reload waits for an empty queue); messages the user sends during a hold merge into the retried turn and share its one retry; chat's queue alarm (12) and watchdog's backlog alert (10) do not know about the hold. Test: `agent/test/chat-quota-hold.test.mjs`. Its end-to-end cases run the real supervisor under a throwaway HOME with `EDVA_HOME` removed from the child's environment (it outranks HOME in `lib/root.cjs`) and `SUPABASE_URL` pointed at a closed local port, so no caller's environment can make the test post into a real chat; a decoy installation with a key proves it. The ops supervisor tests (`supervisor-quota-hold`, `supervisor-hang-dead-letter`) drop `EDVA_HOME` the same way. A scratch copy of the repo is not a sandbox: it carries `.env`.

**A dropped turn is dead-lettered, and the user's own request gets one retry.** The turn watchdog (`turn-watchdog.mjs`) requeues a hung turn once and drops it on its second hang; detection and that count are unchanged. What follows a drop lives in `dead-letter.mjs`: every dropped item is appended to `data/dead-letter.jsonl` (gitignored by `data/*.jsonl`) with its full content, hang count and reason. If the item is **the user's own request** (structurally: a `gmail:<messageId>` item whose row in the command-channel ledger `email-inbound-handled.jsonl`, written by gmail-source when it dispatched mail addressed to Edva's address, has From = the owner address; no text is read), the supervisor (1) sends the user one plain line on the **main chat** (naming the email by how long ago it was sent, never by its subject: Edva's own subjects can carry sensitive figures, and this line passes the precheck and the lock screen) through `_sendChatNotice`, the supervisor's only non-system send, which is a normal precheck-gated `edva-send-curl --intent stuck-request --evidence-as-of live` (no `--skip-precheck`, `EDVA_INFRA_PROBE` stripped), and (2) pushes a fresh copy onto the **tail** of the queue, flagged `hangRetry: true` / `retryOf: <dropped id>`, so it runs after the work already queued and survives a process restart. The retry's text opens with a `[supervisor] RETRY.` header telling the agent the killed attempts may have done part of the work, listing what Edva's sent-mail log shows sent since the request arrived (marking a reply on that thread) and every `job-run` job started since then (read-only from `data/jobs/`, skipping files whose id-date is older; each shown as STILL RUNNING, `ended (process gone; last status running)` or its final status, with "do not relaunch it, wait for it"), and saying never to send anything twice. The sent-mail check answers `replied`, `not-replied` or `unknown` (log unreadable, a line that does not parse, no Message-ID to match, or a scan that does not reach back far enough). The first chat line promises an answer on the user's thread, so it is skipped only on `replied`. A retried item is dropped on its **first** hang, never retried again, and gets a closing chat line that stands alone (the user may never have seen the first) and says whether anything went back on that thread only when that is known. Every drop alert keeps the phrase "dropping it and restarting" (system-issue-review's generic turn-hang cluster matches it), and the dead-letter step is wrapped so it can never skip the SIGKILL. Everything else that drops (cron jobs, other mail, `email-inbound` escalations, whose allowlist also admits other senders) is dead-lettered only. Events: `turn_watchdog.hang` now carries `hangRetry`/`retryOf`; new `turn_watchdog.dead_letter` and `turn_watchdog.retry_enqueued`; a finished retry emits the usual silent `✅ Recovered`. Chat (`chat-supervisor.mjs`) still drops silently. Test: `agent/test/supervisor-hang-dead-letter.test.mjs`.

Chat (`chat-supervisor.mjs`) is interactive and **never rotates mid-conversation** — it has its own `/compact` guard + the cold-start guard (`maxSessionTurns` 250), no handoff. Force a manual rotation any time with `POST /rotate` (rotates only when idle). Watch `totalDispatches` + `contextTokens` in `/health`.

## Watchdog integration

```bash
SNAP=$(curl -sf http://localhost:9093/health) || { echo "supervisor down"; exit 1; }
LAST_EVENT_AGE=$(echo "$SNAP" | jq '.lastEventAgeMs // 0')
if [ "$LAST_EVENT_AGE" -gt 600000 ]; then
  curl -sf -X POST http://localhost:9093/restart
fi
```
